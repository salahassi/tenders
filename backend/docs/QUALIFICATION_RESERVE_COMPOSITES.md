# Review composites and the remaining source-contract work

The offline reserve now has **42 single-request cases and two two-request review
composites**. Six cases remain outside a faithful current construction. The source
corpus and its oracles are unchanged. A composite is one logical evaluation cell
whose physical model requests must be recorded separately. Construction and
controlled response tests do not establish provider quality, database admission,
human approval or a live campaign.

## Separate review identities

The English and Arabic `summarize_review.review_identity` cases contain two
immutable reviews. `buildReserveReviewSegment` selects each review through actual
`generation.taskInput`; each request has its own review identifier, exact source,
manifest, prompt, schema and phase pins. Both reviews remain in the synthetic
frozen context, but only the selected review appears in that request's evidence.
The original single-request entrypoint still rejects this case.

The composite compiler calls production request preparation and stops before
reservation or sending. Its ordered constituent pins and composite hash preserve
the two physical identities. Reconstruction rejects changed context, reordered
segments, replaced validators and unminted objects. Identity, configuration and
observation snapshots are captured before asynchronous work, so caller mutation
cannot relabel English requests or outputs as an Arabic case.

The output projection requires exactly two explicit observations. Every completed
constituent passes its original schema and domain checks, including its selected
review identifier and exact quotations. The evaluator view concatenates validated
arrays and retains source-keyed lineage and each output hash. It is explicitly a
view of separate outputs, never an invented single provider response. Independent
review also reproduced a projection bug: the domain callback alone could accept
the other frozen review's identifier with its valid quote. The projection now
performs the same selected-evidence base validation as `executeModel` before the
broader immutable-source domain check. The failing control and correction are
retained; the production executor already enforced that order. Actual
downstream `taskInput` assembly preserves directive review identities. A
question-only review remains in its original output and finalization lineage;
this test does not fabricate a directive to make it appear in planning.

Any unavailable, refused, failed or unattempted constituent leaves the composite
incomplete with no success aggregate. A completed sibling is still validated and
hashed. There is no retry or provider call in this helper. For an executing runner,
the first known terminal failure must stop further dependent work and record each
unattempted slot explicitly. That runner and its deadline behavior are not
implemented by offline construction.

## Six remaining cases: behavior and corrective work

The six executable boundary controls exercise the current production helpers in
English and Arabic. Their success means that the documented boundary is
reproduced; it does not mean that the original six semantic oracles passed.

### Scoped addendum: an automatic inventory gap

`generation.nextStage('analysis')` deduplicates requirement identities. Given
faithful independent outputs for the initial specification and Addendum C, it
retains both source-bound requirements. It does not identify the governing
terminal quantity or preserve the unchanged cabinet requirement through an
explicit replacement operation. Two extraction calls alone therefore cannot
establish the frozen oracle's result.

The authority record's `supersedes` field binds a document identifier and content
hash. It does not encode the frozen case's narrower phrase, “observation terminal
quantity only.” Separately, the existing SQL obligation-review mechanism supports
exact-span reviewed interpretations and `supersedes_review_id`, and rejects a
superseded reviewed obligation. This is useful existing authority; it must not be
replaced by filename order, numeric precedence or a model's claim of approval.

The corrective path is a versioned governing-inventory contract. It should retain
all extracted historical obligations and carry an explicit relation between the
old and new exact source spans, affected obligation identity, affected semantic
field, authority decision/revision and current content hashes. A reviewed clause
replacement can reuse the existing obligation-review lineage. An automated
proposal of that relation must remain distinguishable from a confirmed human
interpretation. The inventory consumer must apply only the authorized scope and
preserve unaffected obligations. A remaining conflict should be visible in a
draft and its review questions, not silently resolved or turned into a claim of
approval.

Tests must exercise the canonical SQL admission and generation consumer together:
14 terminals with three cabinets; refusal of a whole-document replacement that
would erase the cabinets; unrelated addenda; source-hash changes; revoked and
stale authority; duplicate/cyclic replacement; concurrent revision changes; and
preserved predecessor evidence. Both languages need independently judged
source-to-obligation outputs. The current corpus's source/gold must remain
retained; any additional typed prerequisite or schedule must be separately
versioned, hashed and reviewed before model outputs are seen.

### Supplier proposal: explicit planning policy, with a missing input capability

Current planning selects requirement sources, review directives and verified
company evidence. It explicitly selects style material only for drafting.
Therefore exclusion of the prior supplier brochure is current policy, not a
random retrieval failure. The frozen case concerns a prior supplier brochure; it
must not be relabeled as a current user instruction, buyer requirement or verified
company capability. Omitting it also cannot qualify the intended source-authority
test.

Supporting this use requires an explicit untrusted supplier-proposal channel in
the frozen planning input. Selection should bind the actual selected document,
its current source role, exact spans and hashes. It may inform a decision marked
as a proposed method while remaining unable to create a buyer obligation or
verified company fact. The proposal's requirement identifiers must remain those
of the buyer inventory. The verifier must receive the same source-role distinction.

Before implementation, define how an uploaded supplier document becomes a
selected planning reference through the existing authenticated input flow. Then
test canonical input selection, both-language proposed/buyer decision boundaries,
injection text, changed or revoked documents, missing references and unchanged
buyer requirements. These changes affect production prompts and runtime sources;
they require separate request/schema pins, native runtime qualification and a
release. They are not included in the qualification-only composite change.

### Citation-only repair: deterministic correction versus a different fault

`executeModel` materializes canonical analysis quotations before validating the
candidate. If a known span has an incorrect quote, the source text is restored
deterministically. The two boundary controls confirm that this restores the
candidate without changing its sibling unit. Requiring an additional model repair
for that fault would undo a useful existing behavior.

A wrong source identifier is a different fault. Its actual diagnostics expand the
repair dependency scope to the affected requirement's text, interpretation and
source semantics. That scope can remain isolated from the sibling requirement,
but it exceeds the frozen case's citation-only allowed path. Narrowing the repair
scope merely to make this fixture run would risk an inconsistent source binding.

The corrective qualification design must distinguish these paths explicitly.
Record canonical quote restoration as a deterministic workflow result with zero
repair-provider calls and unchanged sibling hashes. If model citation repair is
still to be evaluated, add a separately versioned reachable fault whose allowed
scope matches the real task—for example the already qualified draft citation
boundary—or a reviewed analysis identity-repair scenario with explicit dependent
fields. Retain the old six-case limitations and original oracles; do not relabel
a deterministic correction or a broader fault as a pass of the frozen registered
repair request. A future activation contract must account for zero-call
deterministic cells as well as multi-request cells.
