# Interrupted storage retirement qualification

This runbook describes an isolated acceptance workflow, `qualify-storage-retirement.yml`. Its implementation and local checks are separate from an actual hosted result. No hosted run or production retirement is established by adding this workflow. Read the permanent [DigitalOcean access runbook](DIGITALOCEAN_ACCESS_RUNBOOK.md) and the current [implementation checklist](IMPLEMENTATION_CHECKLIST.md) before dispatching a reviewed revision.

The workflow uses the existing GitHub-hosted runner path and the original Kubernetes and managed PostgreSQL certificate authorities. It shares the `tenderdesk-digitalocean-production` concurrency group with deployment and other operations. It never disables certificate verification. The only production database access is the existing bounded schema-catalog observer; it copies no customer rows. All test users, business rows, credentials, storage objects and process mutations belong to a nonce-owned namespace and separate database. No model provider is called.

## What the two jobs establish

The first job reconstructs the exact current reviewed release schema, checks all 24 migration hashes, and starts actual pinned Auth and PostgREST services. Separate Deployments run pinned Storage, the qualified gateway configuration and an idle Python process representing the worker's process-lifecycle boundary. The actual HTTP fixture client runs beside Auth/REST and completes its upload before the deliberate retirement interruption. This does not test an in-flight PUT interruption or application worker capacity. Storage uses a new 1 GiB PersistentVolumeClaim (PVC), which requests a dynamically provisioned volume through the verified DigitalOcean storage class. The fixture creates an actual confirmed Auth user, logs in with a password and bootstraps an Owner membership.

The application creates the file reservation through `source.create`, `opportunity.create`, `delivery.snapshot.prepare`, a canonical backend job claim and `delivery_export_context`. `begin_render_storage_write` records a genuine unknown write before an actual 16 KiB Storage upload. The fixture deliberately omits the completion acknowledgment, records the failure through `fail_delivery_export`, and uses canonical archive, purge preview and purge operations. Those operations leave the uncertain key's genuine 10 MiB cleanup reservation in place. The fixture never inserts or edits an intent, lease, quota counter or cleanup allowance directly.

The unchanged strict retirement coordinator captures the three Deployments and their original Pod and container identities. The fixture adapter installs the qualified retired-key guard using the actual observed storage owner, prepares the canonical private retirement batch, persists process protection journals, and scales all three Deployments to zero. It reads back durable state, confirms the reservation remains, then abruptly exits with code 86. This deliberate interruption bypasses the coordinator's normal restoration block. The workflow accepts exactly that exit code as the interruption checkpoint; it does not count it as successful retirement.

The second job runs on a fresh GitHub runner. It reconstructs no identity from a replacement Pod or local file: it loads the original manifests and container IDs from the nonce-owned Kubernetes Secret. The coordinator requires actual terminal status for those exact processes. `NodeLost`, a missing Pod, a replacement container, a replica count of zero or elapsed time cannot establish process exit.

Only after all original processes have provably exited does the coordinator run the unchanged physical storage helper on the exact PVC. It checks the real uploaded hash and size, removes the key's physical files with filesystem synchronization, removes metadata under the actual storage owner, and rereads physical and metadata absence. Unknown allowance must remain unchanged through those steps. The canonical finish function must release exactly the held amount, close the intent and produce one completion audit. An identical finish replay must leave accounting and audit counts unchanged.

Restoration persists and rereads the complete exit proof before removing any owned Pod finalizer. It restores the original replica counts and verifies readiness. Actual Storage requests then demonstrate that the retired key is denied and a newly reserved canonical key can be uploaded. Read-only physical inspection in the fresh Storage process must find no old-key files or metadata, and must find the new key's exact uploaded bytes and metadata. HTTP status alone is insufficient evidence of physical absence.

## Ownership and recovery

The workflow has no namespace, database, workspace or storage-key input. The first job outputs only its generated eight-character nonce and origin attempt. The fresh job derives the target from the same GitHub run, the trusted origin attempt and that nonce, then verifies source revision, current manifest hash, namespace UID, resource UIDs and the database's exact ownership comment. A later failed-job rerun may use the same origin attempt while retaining the actual executing attempt in the evidence. An unrelated run or a changed source cannot adopt the fixture.

Cleanup uses exact UID and resource-version preconditions. Before ordinary controller, PVC or database deletion, it copies the full original termination journals and confirmed protection removal into the durable state Secret and reads the checkpoint back. A fresh cleanup runner validates those exact proofs and the captured source identities, then continues without trying to restore deleted Deployments. Missing or substituted proof cannot be replaced by a `cleaning` phase or an absent Pod. A failure before any protection was installed has a distinct checkpoint: every original Pod must still be present and running with its captured UID, container IDs and specification, and no protection marker may exist. That checkpoint permits only ordinary isolated-fixture teardown; it is not an exit or quota-retirement proof.

A separate durable cleanup Secret records the PVC and bound PersistentVolume identity before deletion. The same PVC observation supplies the delete operation's UID and resource-version preconditions. A newly bound initial PVC must have its exact claim-bound volume identity validated and read back before deletion; an unbound or already-missing PVC also requires a bounded volume census by its original claim UID. An empty census cannot settle in-flight external volume provisioning: without a proven volume identity, cleanup returns `RETIREMENT_FIXTURE_VOLUME_ALLOCATION_RECONCILIATION_REQUIRED`, retains state and namespace, and cannot certify storage absence or proceed to database cleanup. A later exact claim-owned volume can be journaled and its deletion verified. Cleanup waits for storage clients to stop, confirms the volume is gone, waits for database clients, and executes the existing nonce/comment-guarded database and role cleanup. It confirms that cleanup before deleting the namespace. SQL Job results are retained until namespace cleanup so a later runner can reobserve them.

If captured process termination is unknown, cleanup retains the Pod protection and fails with a fixed reconciliation code. This includes a preparation failure after some protection journals were installed but before all captured processes were stopped; the distinct unprotected path cannot adopt a partially protected state. Do not force-remove that finalizer or treat a missing process record as proof. If a resource create acknowledgment is lost before its UID was durably recorded, automatic recovery fails closed instead of adopting a resource by name. An allocation before the durable interruption checkpoint can therefore require explicit ownership reconciliation. The intentional interruption test qualifies the recorded checkpoint; it is not a claim that every possible provisioning failure has automatic recovery.

The services and private fixture credentials have a bounded lifetime of roughly one hour. A delayed rerun may be able to clean the fixture but cannot claim a successful complete acceptance after those services expire. The workflow never refreshes or extends a failed measurement to manufacture a pass. A changed specification, foreign resource, unproven deletion or absent journal remains an explicit failure.

## Evidence to retain after an actual run

Failed fixture commands report only a fixed phase, command/resource class, exit
status and allowlisted failure category. An exact recognized fixture-writer
failure envelope may also contribute its fixed code and HTTP status. Raw command
arguments, payloads, output, credentials and resource identities remain private.
These fields locate a failed operation; a generic historical failure without
them does not establish a TLS, scheduling, SQL or application root cause.

Retain the exact reviewed source commit, canonical release manifest hash, run link, both job outcomes, original certificate verification, redacted boolean checks, observed recovery duration and verified cleanup result. The public receipt contains no user tokens, database credentials, private keys, object keys or synthetic row identifiers. Private captures and proofs remain in the fixture's Secrets until verified cleanup. Do not publish raw SQL client or application diagnostics.

A passing result qualifies this specific real Kubernetes/PVC interruption, the canonical SQL accounting path, pinned storage/gateway binaries and unchanged coordinator. It does not execute or qualify the fixed production Kubernetes adapter. The synthetic writer is not the application worker and provides no worker capacity measurement. The test does not simulate whole-cluster restore, preserve retirement fences across disaster recovery, or qualify arbitrary file sizes and concurrency.

Recovery time and recovery point objectives have not been supplied by the owner. Report measured elapsed time without assigning a target or calling it a service-level pass. Whole-cluster fence continuity and those objectives remain separate acceptance work.
